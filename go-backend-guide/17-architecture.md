# 17. Архитектура сервисов и основы System Design

## Структура проекта
Официального стандарта нет. Распространённый вариант:
```
myapp/
├── cmd/
│   └── api/main.go          # точка входа: конфиг, сборка зависимостей, запуск
├── internal/                # код, который нельзя импортировать извне модуля
│   ├── config/
│   ├── domain/              # сущности и доменные ошибки (Task, ErrNotFound)
│   ├── service/             # бизнес-логика
│   ├── repository/
│   │   └── postgres/
│   └── transport/
│       ├── http/            # хендлеры, middleware, DTO
│       └── grpc/
├── migrations/
├── proto/
├── Dockerfile
├── docker-compose.yml
├── Makefile
└── go.mod
```
Не усложняй: для маленького сервиса это уже много. Слои добавляй по мере необходимости.
Почитай go.dev/doc/modules/layout — официальные рекомендации.

## Слоистая (clean / hexagonal) архитектура
```
transport (HTTP/gRPC) → service (бизнес-логика) → repository (БД, кэш, внешние API)
```
- Зависимости направлены **внутрь**: service ничего не знает о HTTP и SQL.
- Service зависит от **интерфейсов** репозиториев, объявленных в пакете service. Это даёт тестируемость (моки).
- **Dependency injection через конструкторы:** `NewTaskService(repo TaskRepo, cache Cache, log *slog.Logger)`. Всё собирается в `main.go`. DI-фреймворки (wire, fx) встречаются, но для начала не нужны.
- DTO (структуры для JSON) отдельно от доменных структур.

## Монолит и микросервисы
- Микросервисы: независимые деплой и масштабирование, разные команды. Цена: сетевые ошибки, распределённые транзакции, сложная отладка.
- Начинать почти всегда разумно с модульного монолита.
- Синхронное общение (HTTP, gRPC) против асинхронного (Kafka, RabbitMQ).

## Паттерны надёжности (часто спрашивают)
- **Таймауты** на каждом внешнем вызове.
- **Retry с экспоненциальной задержкой и jitter**, только для идемпотентных операций.
- **Circuit breaker:** после серии ошибок временно перестать ходить в упавший сервис (`sony/gobreaker`).
- **Идемпотентность:** заголовок `Idempotency-Key` для POST (повторный запрос не создаёт дубль платежа).
- **Rate limiting**, **bulkhead** (изоляция ресурсов).
- **Graceful degradation:** Redis упал, а сервис работает через БД.

## Распределённые данные
- **Saga:** распределённая транзакция как цепочка локальных шагов с компенсациями (оркестрация или хореография).
- **Transactional outbox** (см. файл 11).
- **CQRS:** раздельные модели записи и чтения (на уровне понимания).
- **CAP-теорема**, eventual consistency.
- **Репликация** (master–replica, чтение с реплик, задержка репликации), **шардирование** (по ключу, проблемы решардинга).

## System Design: из чего строить
Load balancer, API gateway, stateless-сервисы, кэш (Redis, CDN), БД (SQL или NoSQL, реплики, шарды), очереди, объектное хранилище (S3), поиск (Elasticsearch).
Порядок ответа на собеседовании: требования (функциональные и нефункциональные) → оценка нагрузки (RPS, объём данных) → API → схема данных → высокоуровневая схема → узкие места и масштабирование.

## Задачи
- [ ] ⭐⭐ **Рефакторинг Tasks API.** Разнеси код по слоям: transport / service / repository / domain. Бизнес-правила (например, «нельзя больше 100 незавершённых задач у пользователя») живут только в service. Unit-тесты service на моках, без БД.
- [ ] ⭐⭐ **Idempotency-Key.** Для `POST /tasks`: если запрос с тем же ключом пришёл повторно, вернуть сохранённый ответ, а не создавать новую задачу. Хранение ключей в Redis с TTL 24 часа.
- [ ] ⭐⭐ **Circuit breaker.** Оберни gRPC-вызов Users service в circuit breaker. Останови Users service и посмотри в логах, как breaker переходит в состояния open, half-open, closed.
- [ ] ⭐⭐⭐ **Saga.** Мини-система: Order service → Payment service → Inventory service через Kafka. Если товара нет на складе, платёж отменяется (компенсация), заказ получает статус `cancelled`.
- [ ] ⭐⭐ **System design на бумаге.** Для каждой системы нарисуй схему (excalidraw.com) и опиши текстом по шаблону выше:
  1. Сокращатель ссылок (100 млн ссылок, 10 тыс. RPS на чтение)
  2. Лента новостей соцсети
  3. Чат-мессенджер
  4. Rate limiter как отдельный сервис
  5. Сервис уведомлений (email, push, SMS)
