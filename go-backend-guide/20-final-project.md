# 20. Финальный проект для портфолио

Это главный пункт резюме. Цель — показать, что ты умеешь собрать **production-like** систему, а не только учебные примеры.
Лучше один качественный проект, чем пять недоделанных.

## Вариант A (рекомендуемый): «Сервис бронирования мероприятий»

Пользователи смотрят мероприятия, бронируют места; бронь держится 15 минут до оплаты, затем отменяется автоматически.
Здесь есть всё, о чём спрашивают на собесах: конкурентный доступ к местам, транзакции, кэш, события, фоновые задачи.

### Сервисы
| Сервис | Ответственность | Технологии |
|---|---|---|
| **gateway** | REST API для клиентов, аутентификация (JWT), rate limit | net/http или chi, Redis |
| **users** | регистрация, профили | gRPC, Postgres |
| **events** | мероприятия, места, бронирование | gRPC, Postgres, Redis-кэш |
| **payments** | фейковая оплата (успех или отказ с вероятностью) | Kafka-консьюмер и продюсер |
| **notifier** | «отправка» уведомлений | Kafka-консьюмер |

### Ключевые требования
- [ ] Нельзя продать одно место дважды даже при 1000 одновременных запросов (транзакции, блокировки или оптимистичная блокировка через версию). **Обязательно** тест на это.
- [ ] Бронь живёт 15 минут, потом место освобождается (фоновый воркер или отложенная задача).
- [ ] События `booking.created`, `payment.succeeded`, `payment.failed`, `booking.cancelled` через Kafka с **transactional outbox**.
- [ ] Идемпотентные консьюмеры и `Idempotency-Key` на создание брони.
- [ ] Кэш списка мероприятий в Redis с инвалидацией.
- [ ] Пагинация, фильтры (по дате, городу), валидация.
- [ ] Graceful shutdown во всех сервисах.
- [ ] Метрики Prometheus + дашборд Grafana, трейсинг через Jaeger, структурные логи.
- [ ] Unit-тесты слоя service, интеграционные тесты с testcontainers, покрытие бизнес-логики 70%+.
- [ ] `docker compose up` поднимает всю систему одной командой, миграции применяются автоматически.
- [ ] CI в GitHub Actions: линтер, тесты, сборка образов.
- [ ] OpenAPI-спецификация для gateway, proto-файлы для gRPC.
- [ ] Нагрузочный тест (k6 или hey) с результатами в README.

## План по неделям
1. **Неделя 1:** проектирование: требования, схема БД, API, proto, схема архитектуры. Монорепозиторий, compose с инфраструктурой.
2. **Неделя 2:** users + gateway (регистрация, логин, JWT), events (CRUD мероприятий).
3. **Неделя 3:** бронирование с защитой от двойной продажи, тесты на конкурентность, истечение брони.
4. **Неделя 4:** Kafka, outbox, payments, notifier, идемпотентность.
5. **Неделя 5:** Redis-кэш, rate limit, observability.
6. **Неделя 6:** CI, нагрузочное тестирование, полировка, README.

## Другие идеи (если вариант A не нравится)
- **Маркетплейс:** каталог, корзина, заказы, склад (резервирование остатков), saga заказа.
- **Платёжная система:** счета, переводы, история операций, идемпотентность, двойная запись (double-entry), отчёты.
- **Агрегатор новостей / RSS:** парсеры по расписанию (конкурентность), полнотекстовый поиск (Postgres FTS или Elasticsearch), подписки и уведомления.
- **Мессенджер:** WebSocket, комнаты, история в Postgres, Redis pub/sub для нескольких инстансов, статусы «онлайн».
- **Сервис коротких ссылок с аналитикой:** высокая нагрузка на чтение, Kafka для кликов, ClickHouse для аналитики.

## Чего избегать
- Огромный проект, который не доделан. Сначала сделай рабочее ядро, потом расширяй.
- Код, который ты не можешь объяснить. На собеседовании тебя будут спрашивать про любое решение в проекте.
- Секреты и пароли в репозитории (используй `.env` и `.env.example`).
- Один гигантский коммит. Пиши осмысленные коммиты, работай через ветки и PR.
