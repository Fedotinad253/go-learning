# 11. Kafka и асинхронное взаимодействие

## Зачем брокеры сообщений
Сервисы общаются **асинхронно**: отправитель публикует событие («заказ создан») и не ждёт, кто и как его обработает.
Это развязывает сервисы, сглаживает пики нагрузки и позволяет нескольким потребителям читать одни данные.

## Kafka: понятия
- **Topic** — именованный поток сообщений (лог только на добавление).
- **Partition** — топик делится на партиции; порядок гарантируется **только внутри партиции**.
- **Key** — сообщения с одинаковым ключом попадают в одну партицию (например, все события одного заказа идут по порядку).
- **Offset** — позиция сообщения в партиции. Потребитель коммитит offset, до которого обработал.
- **Consumer group** — группа потребителей делит партиции между собой. Партиций 3, потребителей 3: каждый читает одну. Потребителей больше, чем партиций: лишние простаивают.
- **Rebalance** — перераспределение партиций при добавлении или падении потребителя.
- **Retention** — сообщения хранятся заданное время независимо от того, прочитаны ли они.
- **Replication**, ISR, `acks=all` — надёжность на стороне брокера.

### Семантики доставки
- **at-most-once** — может потеряться (коммит до обработки)
- **at-least-once** — может прийти дважды (коммит после обработки) ← **самый частый вариант**
- **exactly-once** — сложно и дорого

Раз дубли возможны, **обработчик должен быть идемпотентным**: например, хранить id обработанных событий.

### Важные паттерны
- **Transactional outbox:** нельзя атомарно записать в БД и в Kafka. Поэтому событие пишут в таблицу `outbox` в той же транзакции, что и бизнес-данные, а отдельный процесс читает outbox и отправляет в Kafka.
- **DLQ (dead letter queue):** сообщения, которые не удалось обработать после N попыток, уходят в отдельный топик.
- **Retry с backoff.**

### RabbitMQ: отличия
Классическая очередь: сообщение удаляется после подтверждения (ack), маршрутизация через exchange (direct, topic, fanout).
Kafka — лог с хранением и перечитыванием, высокая пропускная способность. Знать отличия полезно; глубоко изучать достаточно что-то одно (чаще спрашивают Kafka).

## Запуск Kafka на Mac
```bash
docker run -d --name kafka -p 9092:9092 apache/kafka:latest

# создать топик с 3 партициями
docker exec -it kafka /opt/kafka/bin/kafka-topics.sh --create \
  --topic task-events --partitions 3 --bootstrap-server localhost:9092

# посмотреть сообщения
docker exec -it kafka /opt/kafka/bin/kafka-console-consumer.sh \
  --topic task-events --from-beginning --bootstrap-server localhost:9092
```
Для удобства есть веб-интерфейсы: Kafka UI (`provectuslabs/kafka-ui`) или Redpanda Console.

## Kafka из Go
Популярные библиотеки: `segmentio/kafka-go` (проще для начала), `twmb/franz-go` (быстрая и полнофункциональная), `confluent-kafka-go`, `IBM/sarama`.

```go
import "github.com/segmentio/kafka-go"

// producer
w := &kafka.Writer{
    Addr:     kafka.TCP("localhost:9092"),
    Topic:    "task-events",
    Balancer: &kafka.Hash{}, // партиция по ключу
}
defer w.Close()
err := w.WriteMessages(ctx, kafka.Message{
    Key:   []byte(strconv.FormatInt(task.ID, 10)),
    Value: payload, // JSON события
})

// consumer
r := kafka.NewReader(kafka.ReaderConfig{
    Brokers: []string{"localhost:9092"},
    GroupID: "notifier",
    Topic:   "task-events",
})
defer r.Close()
for {
    m, err := r.FetchMessage(ctx)
    if err != nil {
        break // ctx отменён
    }
    if err := handle(ctx, m); err != nil {
        // retry или отправка в DLQ
    }
    if err := r.CommitMessages(ctx, m); err != nil { /* лог */ }
}
```

## Задачи
- [ ] ⭐ **CLI-продюсер и консьюмер.** Две маленькие программы: одна шлёт сообщения из stdin, другая печатает полученные. Запусти несколько консьюмеров в одной группе и в разных группах, сравни поведение.
- [ ] ⭐⭐ **Партиции и порядок.** Отправь 100 сообщений с ключами `user-1`..`user-5`. Запусти 3 консьюмера в одной группе и выведи, кто какую партицию читает. Убедись, что порядок для одного ключа сохраняется. Убей один консьюмер и посмотри на ребалансировку.
- [ ] ⭐⭐ **События Tasks API.** При создании, изменении и удалении задачи Tasks API публикует событие (`task.created` и т. д.) с полями `event_id`, `type`, `task_id`, `occurred_at`. Отдельный сервис `notifier` читает их и пишет лог «уведомление отправлено». Оба в docker-compose.
- [ ] ⭐⭐ **Идемпотентный консьюмер.** Notifier хранит обработанные `event_id` в Postgres (таблица с UNIQUE, `INSERT … ON CONFLICT DO NOTHING`). Отправь одно событие дважды: уведомление должно уйти один раз.
- [ ] ⭐⭐⭐ **Transactional outbox.** Tasks API пишет задачу и событие в таблицу `outbox` в одной транзакции. Фоновый воркер раз в секунду выбирает неотправленные записи (`FOR UPDATE SKIP LOCKED`), отправляет в Kafka и помечает их отправленными. Проверь: если Kafka выключена, задачи всё равно создаются, а события досылаются после её запуска.
- [ ] ⭐⭐⭐ **Retry и DLQ.** Notifier с вероятностью 30% «падает» при обработке. Сделай 3 попытки с экспоненциальной задержкой, после чего сообщение уходит в топик `task-events.dlq`. Напиши CLI, который перекладывает сообщения из DLQ обратно.
- [ ] ⭐⭐ **Graceful shutdown консьюмера.** По SIGTERM консьюмер дообрабатывает текущее сообщение, коммитит offset и выходит.
